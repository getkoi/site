<span id="outcome"></span>

Start with the free Junji method. Add Yokai when you want automated execution of a prepared project.
Starting with an empty repository? Follow the [greenfield walkthrough](/koi/docs/greenfield) to build
a TypeScript task app, including configuration and real checks.

## Junji alone

You need a repository, a coding agent, and the project's build/test tools. No Koi or Yokai executable is required.

```bash
npx skills add getkoi/junji
```

In your coding agent:

```text
/junji begin
/junji plan
/junji refine
/junji next
```

`begin` creates `.koi/run/` and surveys the repo. `plan` defines the work and runnable verification
commands. `refine` creates ordered phases with dependencies and human gates. Repeat `next` to implement,
verify and commit one phase at a time. Neither sensor scripts nor strategy/model-tier tags are mandatory.

When every phase is done, use `/junji consolidate` to produce the repo-native deliverable and remove
`.koi/run/`. Use `/junji iterate <request>` first to add more work. All documented verification commands
must pass; destructive or gated actions still require human authorization.

## Add Yokai to a prepared project

Install a Rust toolchain and Git, then clone the [framework repository](https://github.com/getkoi/koi)
and install Yokai:

```bash
git clone https://github.com/getkoi/koi.git
cd koi
./install.sh
```

The installer builds only Yokai. Install and log in to a supported coding agent; see
[agent login](/yokai/docs/cli#agent-login). Return to your prepared project:

```bash
yokai setup --once
```

Choose **One model** or **Use tiers**, configure the agent/models, then select the host or a sandbox.
The [model guide](/yokai/docs/models) offers starting recommendations. Missing sensors are generated
automatically from Junji’s bar and real project commands; existing sensors open for review.
Choose Approve and test to run the exact scripts and save the gate if they all pass. Yokai then
proposes missing phase choices. Review them and choose **Approve and continue**. After readiness
passes, setup offers **Start run** or **Save and exit**.
Every preparation visit ends at the final review. Use the timeline to revisit earlier steps before
choosing Start run. Later bare `yokai` launches reuse approved settings and execute directly.
A failing check stays intact and is reported; setup never weakens it to get a green result.

Yokai reads the repository's METHOD, CONTEXT, backlog and phase plans. The execution machine does not
need the Junji skill installed. Yokai does not take raw goals or arbitrary plans.

## Later launches

```bash
yokai                 # reuse settings and continue
yokai setup           # reopen configuration and review
# Optional read-only diagnostics:
yokai doctor --probe
```

Use **Setup** (`p`) in the cockpit to reopen the [wizard](/yokai/docs/preparation);
it waits for the current phase to finish. Bare Yokai halts at `[gated]` phases. `--allow-gated` explicitly authorizes them for one invocation;
standing directives still apply. Configuration, assessments, gate review and plan import do not grant that approval.

`--headless` and noninteractive startup never prompt or write setup defaults. Prepare and review the
gate interactively and save phase choices approved through the helper or wizard. Assessment YAML
requires no second approval or fingerprint. Changed verification commands or scripts require
`yokai setup`; reconsider phase choices when scope changes warrant it. Sensor commands are reviewed before temporary smoke checks; approval to save is conditional on passing results.

Settings persist in `.koi/yokai.yml`; `.koi/run/yokai.yml` is an optional differences file.
Consolidation removes effort overrides, sessions and accounting but preserves reusable settings,
sensors and sandbox artifacts. See [configuration](/yokai/docs/configuration).

## Existing installations

There is no replacement Koi binary. Run `yokai migrate` for legacy configuration, then `yokai` to review
the gate and phase assessments. Matching legacy receipts become compact gate fingerprints in durable
settings; migrated receipts need an environment smoke review, and stale receipts need reconciliation. Migration preserves active plans, customized method documents, progress and sensors.
[Migration details](/koi/docs/cli).
