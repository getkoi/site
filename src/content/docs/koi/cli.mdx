The Koi executable has been retired. Koi remains the product umbrella and public repository-file
convention. Use Junji directly for method work and Yokai for runtime setup and diagnostics.

## Command changes

- `koi setup` and `koi init` become interactive `yokai` startup or optional `yokai`.
- `koi doctor` becomes `yokai doctor` (`--probe` remains optional).
- `/junji begin` works without installing an executable.

There is no compatibility wrapper, shared installer or generic Koi configuration file.
The normal workflow is Junji preparation followed by either `/junji next` or `yokai`.

## Migrate existing settings

```bash
yokai migrate
```

Migration moves `.koi/run/config.yml` and `.koi/sandbox.yml` into the new layered model:
`.koi/yokai.yml` holds reusable preferences and a nested `sandbox` mapping; optional
`.koi/run/yokai.yml` holds effort differences and phase execution overrides.

Every supported field survives, including timeouts, guides, tier cooldowns and custom sandbox fields.
Original bytes are retained in `config.yml.legacy` and `sandbox.yml.legacy`. Active plans, customized
METHOD/CONTEXT documents, progress and sensors are not regenerated.

Conflicts with new files list the affected field paths and require resolution. Edit the files to
reconcile them, or explicitly choose `yokai migrate --prefer legacy` or `--prefer new`. Nonconflicting
fields survive either choice. Malformed or unreadable files are errors, never defaults. Migration is
repeatable and interrupted writes retain recoverable originals. A different existing backup blocks
migration rather than being overwritten.

Run `yokai` afterward to review the executable gate. Existing annotated plans remain supported.
To adopt the new method during an active effort, merge template changes into your copied method
documents deliberately; preserve custom sections and standing directives. Fresh efforts use the
simplified templates automatically.
