The local execution board is mandatory. Connecting Jira is optional. Network or authentication
failures leave local engineering results unchanged; they do not prevent local work.

## Connect with your board link

After accepting the refined backlog, tell your agent:

```text
/junji connect https://example.atlassian.net/jira/software/projects/APP/boards/2
```

The agent reuses your saved destination and authentication when possible. If you need to sign in,
it guides you through a local browser or hidden credential prompt. Do not paste tokens into chat.
You do not need to write configuration JSON or look up project, account, issue-type or status IDs.

A dedicated host connection agent discovers Jira through MCP, supplied over ACP by the runtime.
It reads the available tool schemas, board filter, project, Reporter, required fields, issue types
and workflows. It recommends a supported parent/child hierarchy for the accepted work and asks you
only about business choices it cannot resolve from context. The effort becomes the parent and its
accepted cards become the children. Existing remote issues and bindings are preserved, not recreated.

Review one readable summary covering:

- The board/project, parent and child types, accepted card count and existing bindings.
- Reporter, required fields, defaults and the fields needed to appear in the board's filter.
- Target statuses, equivalent statuses and the source states from which transitions are allowed.
- The scope of automatic publication, including later accepted cards under the reviewed parent.

Approve that exact configuration and scope before it is saved. Accepting the backlog or saying
“use Jira” is not approval of an unseen connection. Changed board/profile hashes or stale read-only
discovery evidence require a refreshed review. Freshness checks replay the actual discovery evidence,
not a new set of nondeterministic recommendations.

Saving creates no issues. The dedicated host publisher then applies accepted work within the approved
scope. **Setup saved** and **publication verified** are separate results: the agent reports confirmed
issue links and pending/conflicting work from actual evidence and durable bindings/receipts. If no
live publication was checked, it must say so rather than claim success.

`connect` does not move Next action, accept a proposed split, execute code or bypass a human gate.
A failed connection leaves your previous settings and local work available. Reconnect through the
same verb to review publication settings. A different destination requires reconciliation of existing
bindings before it can be saved.

## Who owns progress

Coding phase agents never call Jira tools. During a Yokai run, the supervisor owns verified state
and requests publication; the dedicated host publisher applies it. In standalone Junji, `next`
records local proof only after the documented verification bar, required commit and clean-tree
checks pass, then requests sync. That sync delegates to the host publisher; it does not give the
coding agent Jira access.

The runtime still owns the local board, exact reviewed authorization, verification proofs, stable
bindings, pending operations and durable receipts. A host agent chooses Jira operations using live
MCP schemas, but cannot replace those safeguards with its own judgment. Done requires a matching
local verification proof, not a local done claim, a remote Done status or an agent's self-report.

Each local state has one reviewed remote target; several remote statuses can be equivalent.
Transitions must respect available transitions and reviewed source states. Unexpected human workflow
edits are preserved and reported as conflicts. Remote changes never silently replace local scope,
dependencies, verification requirements or execution gates. Imports require explicit selection and
do not authorize execution.

Stable markers and bindings preserve partial hierarchies across retries. Uncertain creation must be
reconciled before retrying; it is not an excuse to create another issue. Binding an existing issue or
authorizing a retry after confirming absence needs evidence and review. Pending delivery never changes
engineering results and survives consolidation. Previously accepted cards can report progress while
a replacement proposal is under review; `BACKLOG.proposed.json` never publishes.

## Credentials stay on the host

Profiles remain in `.koi/adapters/jira.json`; bindings, verification proofs and receipts remain under
`.koi/visibility/`. Reconnecting preserves these files and existing remote identities.

Credentials remain in the host OS store: macOS Keychain or Linux Secret Service. A local MCP transport
supplies tool access to the dedicated host agent through ACP. Tokens are not placed in model prompts,
repository files or the coding sandbox. A rebuilt macOS binary may need Keychain approval again.
Headless execution reuses existing authentication and never opens sign-in.

## Advanced authentication support

These retained commands are for authentication support when login is needed, not the connection
workflow. Normally `/junji connect` handles the handoff. Do not change auth methods just to retry setup.

Browser OAuth is the default. To explicitly return to OAuth:

```bash
junji-board visibility login --auth-method oauth
```

If OAuth is unavailable, an organization admin can enable **Allow API token authentication** in the
Rovo MCP server. Create a scoped **MCP v2** token with `read:jira:agent-interface`,
`write:jira:agent-interface` and `search:jira:agent-interface`. The agent resolves the selected site's
cloud UUID from available metadata; the user should not have to hunt for technical identifiers.

```bash
junji-board visibility login --auth-method api-token \
  --site https://example.atlassian.net --cloud-id CLOUD_UUID
```

The local prompt collects the account email and hides token input. Login verifies read access
before replacing stored credentials. Never put the token in arguments or chat. Repeat secure login
for expired credentials. Pre-registered OAuth clients can use `--client-id` and, when required,
`--redirect-port` matching their registered loopback callback. These auth commands are also available
under `yokai visibility`.

[Atlassian's API-token guide](https://developer.atlassian.com/cloud/rovo-mcp/guides/configuring-authentication-via-api-token/)
covers token creation and organization settings.

## Internal agent tooling

`prepare`, `review` and `sync` remain compatible runtime operations under `junji-board visibility`
and `yokai visibility`. They are agent tooling, not an engineer checklist. Preparation delegates
read-only MCP discovery to the host connection agent; review saves the exact approved Profile only
after freshness and authorization checks; sync delegates publication to the dedicated host agent.
Optional `--agent` / `--model` select an existing host ACP agent, not an additional setup requirement.

Status, import and uncertain-operation reconciliation remain available for support. No runtime command
or remote issue grants execution permission. Standalone Junji does not require a Yokai executable.
