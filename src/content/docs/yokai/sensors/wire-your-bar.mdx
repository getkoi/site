Run interactive `yokai sensors`, or use the optional `/yokai sensors` helper to prepare proposals.
The executable uses the same sensor policy without requiring installed skills. Junji's CONTEXT
verification bar defines requirements; actual project commands provide the checks.

## Establish coverage

Inspect repository instructions, CI workflows, package scripts, tool configuration and tests.
For each sensor, show its source path and command, the requirement it covers, its working directory
and prerequisites. Reference commands that actually exist. Recipes are examples, not evidence that
a project has the corresponding check.

Report a missing required check as a gap and propose implementing it separately. A gap blocks saving
a complete gate. Do not substitute grep assertions, inline test programs or always-pass scripts.
Commit conventions normally belong to commit review or an existing commit-range check; do not test
all repository history or fail an unborn repository. Human approval and setup remain separate.

## Review, smoke, approve

1. Propose one atomic `.sh` wrapper per concern, retaining existing checks unless a concrete defect,
   duplicate or obsolete requirement justifies replacement or removal. Show reasons explicitly.
2. Review exact commands, coverage and removals before running anything.
3. Smoke-run temporary copies of every proposed script in the selected host or sandbox environment.
   Report every result, even after a failure.
4. Fix shell defects, wrong working directories and missing prerequisites through a new proposal.
   Preserve genuine product-check failures; approval does not turn them green.
5. Approve the results and save the reviewed gate. Declining review leaves existing sensors intact.

Yokai preserves replaced or removed originals in unique hidden `.before-review-*` backups. An
omitted sensor cannot silently disappear. Failure alone is never a reason to weaken or remove one.

## Wrapper contract

Yokai supplies the repository root as cwd to both temporary and saved scripts. Do not derive it
from `$0`, `BASH_SOURCE` or the script directory: temporary copies live at a different depth.
For an existing `package.json` test command:

```bash
#!/usr/bin/env bash
set -euo pipefail
# Source: package.json scripts.test; covers unit tests.
exec npm test
```

Use an explicit `cd path/to/subproject` only when the source command requires it. Keep scripts
compatible with the selected shell: macOS host Bash may be 3.2, which lacks `${value,,}` and
associative arrays. Syntax validation alone does not prove the command works.

Checks observe and fail. They must not install dependencies, fetch advisory databases, run fixes,
rewrite snapshots or configuration, commit or push. Bake prerequisites into the sandbox image or
prepare the host before smoke review. Do not add a clean-tree sensor; normal implementation and
temporary review files legitimately make the tree dirty.

Prefix names such as `10-fmt.sh`, `20-lint.sh` and `30-unit-test.sh` when order matters. The regular
runtime gate is fail-fast; preparation collects all smoke results.

## Review metadata

Yokai stores versioned bar and script fingerprints under `gate_review` in `.koi/yokai.yml`.
Changing checks or verification requirements requires review again. Never hand-edit fingerprints.
For the legacy `.koi/gate-review.yml`, `yokai migrate` converts only an exact matching receipt;
stale receipts stay available for reconciliation. See [migration](/yokai/docs/configuration#migrate-an-existing-installation).
